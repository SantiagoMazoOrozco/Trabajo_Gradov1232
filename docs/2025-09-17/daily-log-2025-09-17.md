# Registro diario — 2025-09-17

Este registro resume el trabajo realizado hoy, con el "por qué" de cada cambio y las rutas a los archivos correspondientes.

## Objetivo del día

Hacer que la ejecución del pipeline sea totalmente observable y controlada: registrar eventos con agentes/acciones, monitorear recursos con marcas de tiempo, visualizar incidentes (reintentos/fallos), y generar un reporte HTML explicativo. Además, parametrizar los nombres de agentes para futura integración con JADE.

## Cambios principales

1) API y simulación
- Se añadió un endpoint `/pid` al servicio FastAPI para identificar el proceso y poder monitorear su memoria (archivo: `python-analysis/api/main.py`).
- El simulador ahora emite eventos START/DONE con `agent`, `action`, y explicaciones en los eventos DONE (`why`) (archivo: `python-analysis/simulate_experiment.py`).
- Se implementaron eventos de RETRY_ y FAILURE_ con sugerencias y marca `fatal` cuando aplica, para trazabilidad de incidentes (archivo: `python-analysis/simulate_experiment.py`).
- Los nombres de agentes son configurables mediante `python-analysis/agent_config.json`, usados en los logs (archivo: `python-analysis/simulate_experiment.py`).

2) Monitoreo y timeline
- Se creó/actualizó `python-analysis/monitor_run.py` para muestrear CPU y memoria del proceso API, y dibujar `timeline.png` con líneas verticales en eventos START y marcadores de color para RETRY (naranja) y FAILURE (rojo).

3) Reporte HTML
- `python-analysis/report_run.py` genera `report/report.html` con:
  - Tabla por etapa (Agente, Acción, Inicio/Fin, Métricas/Resultados, y el "por qué").
  - Imagen del timeline embebida.
  - Sección de "Glosario de porqués y decisiones".
  - Sección de "Incidentes y acciones".

4) Agregación de métricas
- `python-analysis/aggregate_metrics.py` agrega métricas entre corridas en `data/results/aggregate_metrics.csv` para comparar tiempos y calidad.
- Se añadió `matplotlib` a `requirements.txt`.

5) Automatización de ejecución controlada
- `scripts/run_experiment.ps1` ahora puede:
  - Iniciar el API, correr el simulador, parar el API.
  - Habilitar monitoreo y generar reporte.
  - Opcionalmente "quiesce" el sistema y restaurarlo al finalizar.
- Scripts `scripts/quiesce_system.ps1` y `scripts/restore_system.ps1` ajustan plan de energía, pausan OneDrive y detienen/recuperan servicios selectos.

6) Documentación
- `docs/runbook_fase1.md` explica cómo ejecutar en entorno controlado, habilitar monitoreo, interpretar el timeline, y generar el reporte.
- `docs/architecture.md` y `docs/message-protocol.md` describen la arquitectura multi-agente y el protocolo de mensajes.
- `docs/dataset-catalog.md` y `docs/fase0_documentacion.txt` complementan la Fase 0 con el dataset y la narrativa.

## Razonamiento (por qué se hizo)
- Observabilidad: correlacionar uso de CPU/memoria con etapas del pipeline permite explicar resultados y detectar cuellos de botella.
- Reproducibilidad: el runbook y los scripts estandarizan la ejecución, minimizando interferencias del sistema.
- Trazabilidad: los eventos START/RETRY/FAILURE/DONE, junto con el "why", documentan decisiones y problemas.
- Preparación para JADE: parametrizar nombres de agentes facilita la futura integración con una plataforma de agentes.

## Cómo probar (resumen)
- Usar `scripts/run_experiment.ps1` con flags de monitoreo y reporte. El reporte quedará en `data/results/<ExperimentId>/report/report.html` y el timeline en `data/results/<ExperimentId>/monitor/timeline.png`.
